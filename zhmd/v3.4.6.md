# v3.4.6 - SDXL anytest LoRA 型 ControlNet 在 ConvRot INT8 / Hybrid ConvRot NVFP4 基座上的完整修复指南

## ① 问题是什么

LoRA 型 ControlNet `CN-anytest_v4-marged_am_dim256.safetensors` 在 HSWQ 量化的 SDXL 基座上出现了两轮症状：

1. **完全无效**（由 `c60bb0b` 修复）—— 无任何报错，流程正常跑完，但图像完全忽略提示图。
2. **线稿锁定 / 不染色 / 强度滑块失效**（由 `152c1dc` 修复）—— 控制已经可见地生效（结构跟随提示图），但输出仍是黑白的：**没有染色**，且**强度滑块看起来完全失效**。

来自用户真实工作流的决定性观察（同一基座、同一提示图、强度 1.0）：

| ControlNet 文件 | 类型 | 输出 |
|---|---|---|
| `CN-anytest_v4-marged_am_dim256.safetensors` | LoRA 型（`ControlLora`） | 接近灰度（sat ~1.3/255）—— 线稿锁定 |
| `CN-anytest_v4-marged_pn_dim256.safetensors` | LoRA 型（`ControlLora`） | 接近灰度（sat ~1.3/255） |
| `CN-anytest4_illustrious2_A_convrot_int8.safetensors` | 全量型（`ControlNet`） | 正常染色（sat ~59/255） |

因此故障只与 **LoRA 型路径 + checkpoint 加载器节点** 的组合有关，与 control 文件本身无关。

---

## ② 根本原因

### 第一层 —— `HSWQCheckpointLoaderSDXL` 忽略了 `weight_dtype="int8_tensorwise"`（主因）

该节点直接调用 `comfy.sd.load_checkpoint_guess_config(...)`；对于 `int8_tensorwise` 它传入的是 `model_options={}`（只有 fp8 才会设置 dtype），因此 **INT8 Conv2d 加载路径从未被执行**。

ConvRot INT8 checkpoint（如 `JANKUTrainedChenkinNoobai_v777_hswq_r32_1off_convrot_int8.safetensors`）将量化的 **Conv2d** 层以 sidecar 格式存储：

| checkpoint 中的键 | 内容 |
|---|---|
| `X.weight` | 原始 int8 qdata |
| `X.weight_scale` | 每张量 scale（如形状 `(320,1,1,1)`） |
| `X.comfy_quant` | JSON：`{"format":"int8_tensorwise","convrot":true,"convrot_groupsize":64}` |

缺少 INT8 Conv2d 加载作用域（`_int8_quant_conv_scope()`）时，这些层会以 **原始 qdata 被重解释为 fp16（absmax ~127，std ~30）** 保留在加载后的模型中。已在用户真实基座上验证：

- **基座 UNet 单独前向 → `nan=65536`**（走这条加载路径时基座本身就已损坏）
- **ControlLora 借用的权重** 对这些 conv 是 ±127 的垃圾值 → 控制输出 **爆炸**：`[731, 123352, 183752, NaN]`（对照正常的全量型 ControlNet 为 `[325, 616, 944, 1414]`）

爆炸的控制信号（即使强度 0.1，`0.1 × 183k` 也远超正常的 `~1k`）会**完全压过模型**：输出变成提示图的副本（黑白线稿），模型无法再添加颜色，强度滑块也看不出任何效果。

### 第二层 —— ControlLora 借用权重的反量化（由 `c60bb0b` 修复，仍然必需）

`ControlLora.pre_run` 会把基座 UNet 的 `state_dict()` 借入一个**浮点** `ControlLoraOps` control model。在量化基座下：

- **Bug A：** comfy-kitchen 的 `dequantize_int8_convrot_weight_dtype` 仅支持 2D —— 4D Conv2d 会抛 `NoCapableBackendError`，旧 wrapper 回退为 **原始 qdata（±127）**。
- **Bug B：** HSWQ 武装的 Conv2d（`_hswq_convrot=True`）将权重保留在**旋转基**中 —— `qt.dequantize()` 会成功但返回 `W_rot`，对浮点 control model 是错误的。

v3 wrapper 现在会收集 `(qt, module)` 对，用 `_manual_qt_dequant`（qdata × scale）反量化，并在模块被武装时对 4D Conv2d 权重做**逆旋转**（`_unrotate_conv2d` 与 `native_convert_int8.rotate_weight_conv2d` 完全镜像）。启动时无条件安装。

### 第三层 —— Hadamard 设备不匹配（由 `152c1dc` 修复）

`_unrotate_conv2d` 在 **CPU** 上构建 Hadamard 矩阵，而 qdata 可能在 **CUDA** 上 —— 采样时 `ControlLora.pre_run` 内抛出 `RuntimeError: Expected all tensors to be on the same device`。`_regular_hadamard` 现在会取 qdata 所在设备。

所有检查都在用户的真实配置上运行：`JANKUTrainedChenkinNoobai_v777_hswq_r32_1off_convrot_int8.safetensors` + `CN-anytest_v4-marged_am_dim256.safetensors`，16 步 euler/simple，cfg 5.0，denoise 1.0。

## ⑤ 使用说明

1. **更新后请重启 ComfyUI** —— 长时间运行的服务器会保留旧的（已损坏的）代码在内存中。
2. 用 **`HSWQ Checkpoint Loader (SDXL)`** 并选择 `weight_dtype = int8_tensorwise` 加载 INT8 checkpoint（现已走 INT8 感知的加载器）。仅 UNet 的文件继续用 `load_unet_hswq_weight_dtype` / `UNETLoader`。
3. 强度滑块恢复正常。
4. 如果更新后 LoRA 型 ControlNet 仍然“锁定”，请检查基座是否通过上述 INT8 感知路径之一加载。
5. 全量型（非 LoRA）ControlNet 路径从未受影响，保持不变。
