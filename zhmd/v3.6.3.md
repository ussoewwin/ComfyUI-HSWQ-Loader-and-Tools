# v3.6.3 发布说明（中文）

## 概述

**新增 SDXL ConvRot INT8 CLIP 支持。** 检查点内嵌的 SDXL 文本编码器（CLIP-L `conditioner.embedders.0` 与 CLIP-G `conditioner.embedders.1`）现在可量化为 **ConvRot INT8**，并在 ComfyUI 中正确加载与推理。此前 SDXL 的 CLIP 只能保持 FP16；直接将其 int8 化会导致文本条件崩塌（cos ~0.10）或直接崩溃。

本次更新在加载器侧补齐了 SDXL 文本编码器缺失的量化元数据通路，并配套提供基于规则的 FP16 保护转换脚本。实测表明：**带保护的 SDXL CLIP INT8 与 FP16 CLIP 在潜空间轨迹上统计上不可区分。**

---

## 技术背景：为何 SDXL（与 SD1.5）需要此项支持，而 Krea2 / Z Image 不需要

ComfyUI 在构建文本编码器时，只有在 `model_options["quantization_metadata"]` 被设置的情况下才会使用 `comfy.ops.mixed_precision_ops`（量化感知算子），否则使用 `comfy.ops.manual_cast`（普通浮点算子）。

- **Krea2 / Z Image**：使用 Llama 系文本编码器，其加载路径通过 `llama_detect()` 在内部调用 `comfy.utils.detect_layer_quantization()`，自动检测量化并返回 `llama_quantization_metadata`，由 `sd.py` 分支直接传入文本编码器。**量化检测已内建于加载路径。**
- **SD1.5（CLIP-L）/ SDXL（CLIP-L + CLIP-G）**：使用专用的 `SDClipModel` / `SDXLClipModel` 类，`sd.py` 的对应 CLIPType 分支**从不调用 `detect_layer_quantization`**（仅 MINIMAX 与 MING 分支调用）。因此 int8 权重及其 `.comfy_quant` / `.weight_scale` 伴随张量从未被消费，会以原始 fp16 载入（absmax 127），文本条件随之崩塌。

因此 SDXL（与 SD1.5 一样）必须由加载器侧注入量化元数据。

---

## 本次修复的三个独立故障（均为实测定位）

### 1. 量化元数据未注入（int8 权重以 fp16 载入）

SDXL 文本编码器加载路径从不设置 `model_options["quantization_metadata"]`，CLIP-L / CLIP-G 类也无自检测机制。结果：CLIP 的 int8 权重被当作 fp16 载入（absmax 127），条件崩塌。

**修复**：`nodes/sdxl_convrot_int8/sdxl_clip_quant.py` 包装 `comfy.sd.load_state_dict_guess_config`，当包内携带 `conditioner.embedders.*` 的 `.comfy_quant` 层时，通过 `te_model_options["quantization_metadata"]` 注入 CLIP 限定元数据，使 `SDXLClipModel` 以 `mixed_precision_ops` 构建 `clip_l` 与 `clip_g`。

### 2. `clip_l.text_projection` 空权重崩溃

SDXL 的 CLIP-L 不在检查点中存储 `text_projection`。FP16 路径下 ComfyUI 会将其构建为未使用的全零 Linear；而在 `mixed_precision_ops` 下，该量化 Linear 的权重保持为 `None`，前向传播时报 `'NoneType' object has no attribute 'device'`。

**修复**：加载后按 FP16 路径补全 `clip_l.text_projection.weight`（768×768 全零）。CLIP-G 自带 `text_projection`（1280×1280），不受影响。

### 3. CLIP-G 伴随键未随权重转换（黑图）

`transformers_convert`（由 `SDXL.process_clip_state_dict` 调用）会把 CLIP-G 的 `.weight` 重写为 HuggingFace 布局（`text_model.encoder.layers.N.*`），但**不会**移动 `.comfy_quant` / `.weight_scale` 伴随键，它们仍停留在 OpenAI-CLIP 路径。量化算子模块因此找不到对应元数据，int8 权重以原始 fp16 载入，条件爆散（absmax ~1.7e6，cos -0.018），输出全黑。

**修复**：`_remap_clipg_companion_keys()` 在（仅重写权重的）转换运行前，将 CLIP-G 的 `.comfy_quant` / `.weight_scale` 移动到与 `.weight` 相同的 HF 布局。

| 项目 | 修复前 | 修复后 |
| :--- | :--- | :--- |
| 包条件 absmax | 1,749,812 | 126.44 |
| cos（对比 FP16） | -0.0184 | 1.0000 |
| 图像 | 全黑 | 正常 |

## FP16 保护规则（与模型无关，实测得出）

在四个 SDXL 检查点（waiIllustrious / waiREALCN / animemix / bluePencil）上计算 CLIP Linear 层的风险指标（kurtosis / outlier_ratio = absmax/std），保护集在四个模型上结构一致：

**保持 FP16（保护）**：

- CLIP-L：`embeddings.token_embedding`、`embeddings.position_embedding`、`encoder.layers.0.mlp.fc1`、`encoder.layers.0.mlp.fc2`
- CLIP-G：`token_embedding`、`transformer.resblocks.*.mlp.c_proj`（全部）、`transformer.resblocks.{2,29}.attn.out_proj`

CLIP 其余部分为完整 ConvRot INT8。

转换脚本：`hswq/sdxl/quantize_sdxl_clip_int8.py`（`is_protected_clip_weight` + `quantize_clip`）。与原生转换器相同的打包数学（Hadamard 旋转 → 逐通道 INT8 → `.comfy_quant` 标记，自适应 gs 256/64/4）。在 re597 包上：133 层 ConvRot INT8 + 38 层 FP16 保护 + 90 层保持原样（norm/bias/1D）。

## 实测结果（25 seed × 25 step，1024×1024，dpmpp_2m / karras）

| 条件 | mean final-cos | same-image | 分叉 | 速度 |
| :--- | :--- | :--- | :--- | :--- |
| FP16 CLIP（基线） | 0.96230 | 14/25 | 0/25 | 9.37s |
| **CLIP INT8（带保护）** | **0.96223** | 13/25 | **0/25** | **7.75s（+17.2%）** |

CLIP INT8 与 FP16 CLIP 的余弦差为 **-0.00007**（实质为零），分叉 0/25。即：在保护集下，将 CLIP 量化为 ConvRot INT8 对潜空间轨迹几乎无影响，同时保留 INT8 的体积与速度收益。

## 向后兼容

- **旧工作流**：`weight_dtype` 为 `default` 或旧值 `int8_tensorwise` 时，SDXL 加载器仍按 ConvRot INT8 路径处理；新的 `SDXL ConvRot INT8` 标记为新增选项，两者均被接受。
- **FP16 检查点**：无 CLIP 量化层的普通检查点不受影响（加载器包装仅在检测到 `conditioner.embedders.*` 的 `.comfy_quant` 层时生效）。
- **其他系列**：SD1.5 / SD3 / FLUX / Z Image / Krea2 / Qwen 的加载路径与本次修改完全隔离，字节级无变化。
