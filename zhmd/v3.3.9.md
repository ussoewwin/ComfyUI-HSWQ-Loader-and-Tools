## 1. 出了什么问题

### 问题 1：Krea2 ConvRot INT8 极度缓慢（主要症状）

更新到 ComfyUI 0.30.x 系列后，Krea2 ConvRot INT8 推理变得极度缓慢。有两个根因。

**(a) 每次 `load_models_gpu` patch 调用时进行全模块扫描**

`patches/comfy_quant_int8.py` 对 `comfy.model_management.load_models_gpu` 做了 monkey-patch，**每次调用**都会执行：

- `_model_has_int8_quantized_weights(model)` — 通过 `model.named_modules()` 遍历**所有模块**（Krea2 有数千到数万个），搜索 QuantizedTensor
- `_model_is_nunchaku_svdq(model)` — 同样的全模块扫描

在 ComfyUI 0.30.x 中，模型加载/内存管理频率增加，这些 O(n) 扫描每次都执行，累积成巨大开销。

**(b) 每次 forward 传递时 CPU→GPU 传输 Hadamard 矩阵**

ConvRot（Hadamard 旋转）将激活旋转为 `x_rot = x @ H`。旧的 `rotate_activation()` 每次都调用 `h_matrix.to(dtype, device)`，在每次 forward 传递时将 CPU 上构建的 Hadamard 矩阵传输到 GPU。此外，HSWQ 注入的 Conv2d forward 也每次调用 `build_hadamard(..., device="cpu")`。GPU 传输涉及设备同步；开销随层数 × 步数倍增。

### 问题 2：ZI NVFP4 显存增长（次要症状）

`nodes/zimage_nvfp4/nvfp4_lora_bake.py` 的 `install_load_models_gpu_bake_hook` 在每次 `load_models_gpu` 调用时扫描**所有 current_loaded_models**：

- `_nvfp4_convrot_diag(model)` — 全模块扫描（无缓存）
- `run_zimage_nvfp4_lora_bake_on_patcher()` — 回退路径调用 `_patcher_has_quant_via_keys()`，遍历**所有 LoRA patch 键**，对每个键调用 `get_key_weight()`（昂贵的 QT 解包）

重复执行导致 GPU 内存碎片和不必要的权重移动，显存占用持续增长。

### 问题 3（潜在 Bug）：`get_hadamard_on_device` 被引用但未定义

在第一个修复提交 `21792a8` 中，`patches/comfy_quant_int8.py` 中 HSWQ 注入的 Conv2d forward 被改为调用 `nc.get_hadamard_on_device(...)`，但在 `native_convert_int8.py` 中**添加函数定义**的 patch 静默失败（PowerShell `Replace` 中的 CRLF 行尾不匹配）。只有 `_HADAMARD_GPU_CACHE` 字典（+3 行）被提交。

- Krea2（DiT）不使用 Conv2d 注入路径，因此没有观察到症状（"速度恢复"看起来是正确的）
- **使用 SDXL ConvRot INT8 会在首次 forward 时触发 `AttributeError`** — 潜在 Bug

### 问题 4（潜在 Bug）：`weight_inner` 被引用但未定义

在同一提交 `21792a8` 中，`_bake_int8_patches_on_dynamic_patcher` 将 `isinstance(weight, QuantizedTensor)` 改为 `isinstance(weight_inner, ...)`，但添加定义行 `weight_inner = weight.data if hasattr(weight, "data") else weight` 的 patch 未被应用（"pattern not found"）。

- SDXL / INT8 + LoRA Dynamic bake 路径会触发 `NameError` — 潜在 Bug

### 问题 5（兼容性）：ComfyUI 0.30.2 API 变更

- `mixed_precision_ops` 的 `disabled` 参数在 0.30.2 中应为 `set`（旧 HSWQ 代码传入 `[]`）
- `LowVramPatch.__call__` → `comfy.lora.calculate_weight` 新增 `original_weights` 参数
- 0.30.2 中量化权重可能存储为 `Parameter(QuantizedTensor)`，因此 `isinstance(w, QuantizedTensor)` 单独检测会失败
- `_quantized_weight_state_dict` 新增 `extra_quant_params` 参数
- LoRA 模块迁移至 `comfy.weight_adapter.lora`

# GPU-side cache: avoids CPU→GPU transfer on every rotate_activation call.
# Keyed by (size, device_str, dtype) — same as CPU cache but on target device.
_HADAMARD_GPU_CACHE: dict[tuple[int, str, torch.dtype], torch.Tensor] = {}

#### (b) 新增：`get_hadamard_on_device()`（紧随 `build_hadamard` 之后）

```python
def get_hadamard_on_device(
    size: int,
    device: str | torch.device = "cpu",
    dtype: torch.dtype = torch.float32,
) -> torch.Tensor:
    """Return Hadamard matrix on target device, with GPU-side caching.

    Builds on CPU (via build_hadamard) once, then transfers to the target
    device and caches there. Subsequent calls with the same
    (size, device, dtype) hit the GPU cache and skip CPU→GPU transfer.
    """
    cache_key = (size, str(device), dtype)
    cached = _HADAMARD_GPU_CACHE.get(cache_key)
    if cached is not None:
        return cached
    h = build_hadamard(size, device="cpu", dtype=torch.float32)
    h = h.to(dtype=dtype, device=device)
    _HADAMARD_GPU_CACHE[cache_key] = h
    return h
```

#### (c) `rotate_activation()`（切换到 GPU 缓存）

```python
def rotate_activation(
    x: torch.Tensor, h_matrix: torch.Tensor, group_size: int
) -> torch.Tensor:
    """Online Linear: x_rot = x @ H (last dim = features)."""
    orig_shape = x.shape
    features = orig_shape[-1]
    if features % group_size != 0:
        raise ValueError(f"features {features} not divisible by group_size {group_size}")
    group_count = features // group_size
    x_grouped = x.reshape(-1, group_count, group_size)
    # GPU-cached Hadamard: build/transfer once, reuse on every call
    h = get_hadamard_on_device(group_size, device=x.device, dtype=x.dtype)
    return torch.matmul(x_grouped, h).reshape(orig_shape)
```

## 4. 逐项变更说明

### 4-1. GPU Hadamard 缓存（Krea2 INT8 速度的主要修复）

- **修复前**：ConvRot 通过 Hadamard 矩阵 H 旋转激活。旧实现在 CPU 上构建 H（`build_hadamard(device="cpu")`），在每次 forward 传递时通过 `h.to(dtype, device)` 传输到 GPU。GPU 传输涉及设备同步；开销随层数 × 步数倍增。
- **修复后**：`get_hadamard_on_device()` 按 (size, device, dtype) 元组生成 GPU 端矩阵并缓存在 `_HADAMARD_GPU_CACHE` 中。后续调用命中缓存，零传输。
- **效果**：Krea2 ConvRot INT8 推理大幅提速。

### 4-2. 早退 + 缓存（减少 load_models_gpu 开销）

- **修复前**：`load_models_gpu` monkey-patch 运行 `_model_has_int8_quantized_weights` 和 `_model_is_nunchaku_svdq` — 两者都进行全 `named_modules()` 遍历。对于 Krea2 等大型 DiT 模型（数千模块），加上 0.30.x 增加的加载/内存管理频率，总开销显著。
- **修复后**：
  - `_model_has_int8_quantized_weights`：最多检查 200 个模块。如果未找到 QuantizedTensor / `layout_type`，提前返回 False。安全，因为 INT8 模型始终在前几个块中有量化 Linear。
  - `_model_is_nunchaku_svdq`：最多检查 100 个模块。SVDQ 替换整个模型结构，始终出现在早期模块中。
- **安全性**：两者在提前退出时回退到 False（跳过 bake、跳过 handoff），但目标模型始终在前部有量化/SVDQ 模块，实际无风险。已通过 ZI NVFP4 / Krea2 验证。

### 4-3. `Parameter.data` 解包（0.30.2 权重存储格式）

- 0.30.2 中量化权重可能存储为 `Parameter(QuantizedTensor)`。`isinstance(w, QuantizedTensor)` 对 Parameter 返回 False，旧检测失败。
- `hasattr(w, "data") and isinstance(w.data, QuantizedTensor)` 解包 Parameter。`_bake_int8_patches_on_dynamic_patcher` 的 `weight_inner` 起同样作用（其缺失的定义也被修复）。
- 新增 `layout_type` 检查：量化层由 `_load_quantized_module` 设置 `layout_type`，提供快速替代检测。

### 4-4. `disabled` set 统一化（0.30.2 API 契约）

- 0.30.2 `mixed_precision_ops` 将 `disabled` 视为 `set`（使用 `disabled.add("nvfp4")` 等）。旧 HSWQ 代码传入 `[]`，可能导致 `AttributeError`。
- 统一为 `set()` / `set(disabled)` 以确保安全。

### 4-5. `original_weights` 参数（0.30.2 calculate_weight 签名）

- 0.30.2 `comfy.lora.calculate_weight` 接受 `original_weights=None`。旧代码缺失此参数，可能破坏 `model_as_lora` 风格的 patch。
- 保留 `try/except TypeError` 回退以兼容旧版 ComfyUI。

### 4-6. `extra_quant_params`（0.30.2 state_dict 契约）

- 0.30.2 `_quantized_weight_state_dict` 接受 `extra_quant_params`。未显式传入 `("input_scale", "pre_quant_scale")` 时，`state_dict()` 保存可能丢失或混淆额外键。
- 注入的 Conv2d `state_dict` 现在与 0.30.2 Linear 调用形式匹配。

### 4-7. load_models_gpu bake hook 快速跳过（ZI NVFP4 显存修复）

- **修复前**：ZI NVFP4 `install_load_models_gpu_bake_hook` 在每次 `load_models_gpu` 调用时扫描**所有已加载模型**，运行 `_nvfp4_convrot_diag`（全模块遍历）。非目标模型（如普通 SDXL）也被扫描，导致不必要的显存权重移动和碎片。
- **修复后**：
  1. `patches` 和 `_hswq_zi_nvfp4_baked_keys` 都不存在时立即跳过
  2. 跳过非 dynamic 模型
  3. `_nvfp4_convrot_diag` 返回 `has=False` 且无 baked keys 时跳过
- **LoRA 影响**：此 hook 是**第二趟**，拾取 `Dynamic.load` wrapper 已 bake 后的遗留。主 bake 在 `Dynamic.load` wrapper 中无条件运行，跳过此 hook 不影响 LoRA 正确性（用户验证：ZI NVFP4 LoRA OK）。

### 4-8. `__init__.py` 导入/签名（0.30.2 模块重组）

- LoRA 模块在 0.30.2 中迁移到 `comfy.weight_adapter.lora`。两阶段回退：先尝试新路径，ImportError 时回退到旧 `comfy.lora`。
- `_lora_skip_calculate_weight` 的 `intermediate_dtype` 默认值从 `None`（内部替换为 `torch.float32`）改为直接 `torch.float32`，匹配 0.30.2 真实签名。

### 5. Krea2 ConvRot INT8 累积速度退化（第 2 次及之后运行减速 4-7 倍）

#### 症状

第 1 次 Krea2 运行正常（~4s/step）。第 2 次运行步时爆炸：
`4.1s → 16.6s → 9.4s → 22.7s → 26.9s → 15.8s`，逐次恶化。
第 3 次及之后更慢。Z Image NVFP4 运行不受影响。

#### 原因：Z Image `comfy_parity` 包装器在 Krea2 加载时残留

Krea2 的加载路径（`is_int8 and is_convrot and not needs_conv2d`）直接调用 `comfy.sd.load_diffusion_model` — 这是一种"stock load"，不调用 `apply_comfy_quant_int8_patches()`。然而，此路径缺少 SDXL 加载路径中存在的 `_clear_zimage_parity_contamination_for_sdxl()` 调用。

Z Image 运行后，HSWQ 清理过程**未完全移除** Z Image `comfy_parity` 包装器（由 `apply_nvfp4_comfy_parity()` 安装的在线 act rotate），这些包装器残留在 `mixed_precision_ops` 上。当这些包装器存活且 Krea2 stock-loads 时，以下连锁反应发生：

1. **`_load_quantized_module_comfy_only` 在 Krea2 的 INT8 ConvRot 层上触发**
   → `_arm_int8_protect_convrot_after_stock_load()` 在每个 Linear 模块上设置 `_hswq_int8_convrot = True` 并清除 `Params.convrot`。

2. **`_ensure_single_parity_linear_forward()` 将 stock `Linear.forward` 替换为 `forward_parity`**
   → 在线 Hadamard act rotate 包裹每个 INT8 ConvRot Linear 的 forward。

3. **每步 `forward_parity` 构建/缓存 Hadamard 矩阵并通过 `rotate_last_dim()` 旋转输入**
   Krea2 已离线将 ConvRot 烘焙到权重中，kitchen 的 `dequantize_int8_convrot_weight` + `int8_linear` 处理 ConvRot — 因此 `forward_parity` 的在线旋转是多余的（且可能双重旋转）。

4. **HSWQ 清理丢弃 Hadamard 缓存（`_hswq_nvfp4_parity_H`）**
   → 每次运行重建 → CUDA 内存碎片累积。

结果：Krea2 的所有 ConvRot Linear 层（最多 256 层）每步执行不必要的 Hadamard 旋转，CUDA 碎片随每次运行增长，导致步时指数级退化。
