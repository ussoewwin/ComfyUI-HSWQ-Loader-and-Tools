## ① 现象

一直正常运行的ワークフロー突然失败，且发生在 **文本编码器 encode** 阶段——当 CLIP/文本编码器被加载到 **CPU**（例如 `CLIPLoaderMultiGPU` 设 `device=cpu`）时：

```
[ERROR] !!! Exception during processing !!!
self and mat2 must have the same dtype, but got Float and BFloat16
```

```
File ".../comfy/ops.py", line 1461, in _forward
    return torch.nn.functional.linear(input, weight, bias)
```

## ② 根本原因

- `comfy_kitchen` **0.2.36**（随 ComfyUI 2026-09-30 更新）修改了 `TensorWiseINT8Layout.dequantize()`：反量化后会将张量恢复为 **`params.orig_dtype`**（这类 checkpoint 为 bfloat16）。
- `patches/comfy_quant_int8.py` 中 HSWQ 的 INT8 **非对齐 GEMM 回退**把反量化后的权重直接连同 **float32 激活**（CPU 激活为 float32）传给 `torch.nn.functional.linear()`。
- 于是在 CPU 路径上出现：**bfloat16 权重 × float32 激活 → dtype 不一致**。
- **CUDA 不受影响**：对齐路径走真正的 `torch.ops.comfy_kitchen.int8_linear` 内核，CUDA 侧的回退也已把两侧转成 `out_dtype`。因此这是 **仅 CPU、仅回退分支** 的回归。
- 这也解释了「以前能用」：HSWQ 回退一直没做 cast，但在 comfy_kitchen 0.2.36 之前，反量化权重保持激活的 dtype，因此不存在不一致。

## ③ 修复

在 `_patch_comfy_kitchen_int8_gemm_fallback()` 中新增辅助函数 `_dq_linear_dtype_safe(args, kwargs)`：反量化参数后，**将 weight/bias 转换为解析出的 `out_dtype`**（缺省为激活 dtype），再调用 `F.linear`。四处回退调用点全部改用它（非 tensorwise、transposed、K/N 非对齐、内核异常回退）。

- INT8 权重仍以 INT8 常驻 VRAM；只有回退路径会反量化，行为与以往一致。
- CUDA 行为不变（对齐路径仍走真内核）。
- 无 API / 签名变更。

## ④ 验证

- 单元复现：`QuantizedTensor`（TensorWiseINT8Layout，orig_dtype=bf16）× float32 激活 —— 修复前朴素路径抛 `same dtype`，修复后正常计算（输出 float32，误差在 int8 量化范围内）。
- 语法检查（`ast.parse`）通过。
